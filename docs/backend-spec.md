# Setanta Sports Platform — задача для бэкенда

Документ описывает, что должен реализовать бэкенд, чтобы фронт перестал жить на моках.
Фронт готов и работает: React 18 + Vite, SPA, все данные сейчас в `localStorage`.

**Что заменяем на API:**

| Что сейчас                                                         | Где в коде                                                                              | Чем станет            |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------- | --------------------- |
| Вход по хардкоду `admin/admin`, `viewer/viewer`, `adv/adv`         | `src/pages/Login.jsx`, `src/context/AuthContext.jsx`                                    | авторизация с токеном |
| Вся база (бренды, площадки, кампании) в одном ключе `bloom.db.v12` | `src/lib/store.js`, `src/context/DataContext.jsx`                                       | REST                  |
| Медиапланы Live Spot                                               | `src/components/campaigns/CampaignMediaTabs.jsx`, ключ `setanta.campaign.live-spots.v4` | REST                  |
| Логи выходов (SS1/SS2 UZB, Event Promo)                            | `src/components/campaigns/SpotLogTable.jsx`, ключ `setanta.campaign.spot-logs.v1`       | REST                  |
| Файлы (договор, ролик) как base64 в базе                           | `src/components/ui/FilePicker.jsx`                                                      | загрузка в хранилище  |

Начальные данные лежат в `src/lib/seed.js` — их удобно взять как фикстуры для дев-окружения.

## 1. Роли и доступ

Три роли: **admin** (сотрудник площадки), **viewer** (тот же админский обзор, но без права
что-либо менять) и **advertiser** (бренд). У рекламодателя в профиле есть `advertiserId` —
он видит только свои данные.

| Раздел                                                              | admin                | viewer             | advertiser           |
| ------------------------------------------------------------------- | -------------------- | ------------------ | -------------------- |
| Кампании (список, карточка)                                         | все                  | все                | только своего бренда |
| Создание кампании                                                   | —                    | —                  | да                   |
| Редактирование кампании, смена статуса                              | да                   | нет                | нет                  |
| Суммы: правка «к оплате / оплачено», внесение поступления           | да                   | нет                | нет                  |
| Суммы: просмотр «Бюджет / Оплачено» и истории выплат                | да                   | да                 | да                   |
| Рекламодатели, их договоры и реквизиты                              | правит               | только читает      | нет                  |
| Договор: условия (номер, срок, пакет, лиги, скан)                   | правит               | нет                | только читает        |
| Договор: название рекламной кампании и ролик                        | только читает        | только читает      | **правит**           |
| Договор: суммы, поступления, статус оплаты                          | правит               | только читает      | только читает        |
| Договор: история выплат и история смен статуса                      | смотрит              | смотрит            | смотрит              |
| Сводки Spot / Total и отчёты соцсетей                               | правит               | только читает      | только читает        |
| Просмотры (колонка «Просмотры», TV Live Ads Views, устройства, гео) | видит                | **не видит**       | видит                |
| Площадки (`/app/channels`)                                          | правит               | только читает      | читает               |
| Обзор (`/app/overview`)                                             | да                   | да                 | нет                  |
| Отчёт (`/app/reports`)                                              | нет                  | нет                | да                   |
| Медиаплан и логи выходов                                            | правит и импортирует | читает и выгружает | только читает        |

Фильтрация «своих» кампаний обязательна на сервере, а не только на клиенте
(сейчас это делает `src/lib/useScope.js`). Права на запись тоже проверяются на сервере:
`viewer` не должен проходить ни один мутирующий эндпоинт, `advertiser` — только создание
своей кампании.

На фронте это единый флаг `canEdit` в `src/context/AuthContext.jsx`; `isAdmin` там истинен
и для `viewer`, потому что состав экранов у них одинаковый.

**`requisites`** — многострочный текст, по строке на пункт (`ИНН: …`, `Банк: …`, `Р/с: …`,

форма редактирует его как обычный textarea, поэтому на бэке достаточно `text`. Если нужен
разбор по полям — парсить на сервере, фронт отдаёт и принимает строку
(`src/components/forms/AdvertiserForm.jsx`, `requisitesToText`).

**`logo`** — картинка бренда: показывается вместо инициалов в карточках, строках кампаний,
шапке статистики и в профиле рекламодателя. Сейчас это либо путь к файлу в `/public/logos`
(мок), либо абсолютная ссылка на файл, залитый через `POST /files` с `kind=logo`; на бэке —
ссылка из хранилища (см. §6). Пустое значение
допустимо, фронт нарисует инициалы на фирменном цвете (`src/components/ui/Avatar.jsx`).

### 2.3 Contract (договор бренда)

Договоры принадлежат бренду; кампания ссылается на договор по номеру.

| Поле                    | Тип                                    | Комментарий                                                               |
| ----------------------- | -------------------------------------- | ------------------------------------------------------------------------- |
| `id`                    | uuid                                   |                                                                           |
| `advertiserId`          | uuid                                   |                                                                           |
| `number`                | string                                 | уникален **по всей базе**, обязателен                                     |
| `campaignName`          | string                                 | название рекламной кампании, под которую заключён договор                 |
| `legalName`             | string                                 | подставляется из карточки бренда, в форме договора не спрашивается        |
| `package`               | `partner` \| `general` \| `presenter`  |                                                                           |
| `leagues`               | string[]                               | коды лиг                                                                  |
| `start`, `end`          | date                                   | срок договора                                                             |
| `paymentDate`           | date                                   | сроки оплаты; в форме договора не редактируется                           |
| `file`                  | `{ name, url, addedAt }` \| null       | скан договора; `addedAt` — момент загрузки                                |
| `creative`              | `{ name, url, addedAt }` \| null       | рекламный ролик договора; `addedAt` — момент загрузки                     |
| `budget`                | number                                 | сумма договора («Бюджет»)                                                 |
| `spent`                 | number                                 | оплачено; равно сумме `payments`                                          |
| `payments`              | Payment[]                              | история выплат по договору, см. 2.8                                       |
| `paymentStatusByPeriod` | `{ 'YYYY-MM': { status, changedAt } }` | статус оплаты **по месяцам** договора — основное хранилище                |
| `paymentStatus`         | `awaiting` \| `paid`                   | последний по времени статус; им подписана карточка, когда месяц не выбран |
| `paymentStatusAt`       | datetime                               | когда поставили этот статус (может быть задним числом)                    |
| `paymentLog`            | ContractStatusEntry[]                  | история смен статуса, см. 2.9                                             |

**Кто что заполняет.** Условия договора (номер, срок, пакет, лиги, скан, суммы, статус
оплаты) ведёт площадка. `campaignName` и `creative` заполняет **рекламодатель** в своей
карточке договора — у админа этих полей в форме нет, он видит их справкой «От рекламодателя»
(в карточке договора и в карточке бренда). Сервер обязан это проверять: запрос рекламодателя
на договор может менять только `campaignName` и `creative`, всё остальное — только admin.

`addedAt` у файла и ролика показывается в интерфейсе подписью «Добавлен 18.08.2026 23:53» —
в форме загрузки, в карточке договора, в справке у админа и в карточке кампании. Проставляется
в момент загрузки файла, при замене файла обновляется.

### 2.8 Payment — поступление по договору

Раньше поступления жили в кампании, теперь — в договоре (`contract.payments`), список
отсортирован **от первого к последнему** (по возрастанию `createdAt`); нумерация в интерфейсе
идёт от первого платежа. Сортировка стабильная: платежи, внесённые в одну минуту, остаются
в порядке внесения.

| Поле         | Тип      | Комментарий                                                      |
| ------------ | -------- | ---------------------------------------------------------------- |
| `id`         | uuid     |                                                                  |
| `contractId` | uuid     |                                                                  |
| `amount`     | number   | сумма поступления                                                |
| `createdAt`  | datetime | дату и время задаёт пользователь при внесении                    |
| `seq`        | number   | номер внесения: держит порядок платежей, внесённых в одну минуту |

Поступления вносит только admin — в поповере у карточки «Бюджет / Прибыль» договора
(`src/components/campaigns/MoneyPopover.jsx`). Там же вкладка «История выплат»: список
доступен всем ролям на чтение, дату со временем и сумму каждой записи admin может поправить.
`spent` договора должен быть суммой поступлений — считать на сервере.

**Важно:** в историю попадает **любой прирост оплаченного**, а не только поле «Поступление».
Если админ поднял «Оплачено» с 0 до 200 млн руками, это тоже платёж на 200 млн с выбранной
датой. Уменьшение суммы записи не создаёт.

Ошибочное поступление admin удаляет прямо в истории — сумма вычитается из `spent`:

```
DELETE /contracts/:id/payments/:payId     (admin) → обновлённый договор
```

### 2.9 ContractStatusEntry — смена статуса оплаты за месяц

Хранится внутри договора (`contract.paymentLog`), сортировка от новых к старым по `createdAt`.

| Поле         | Тип                  | Комментарий                                                       |
| ------------ | -------------------- | ----------------------------------------------------------------- |
| `id`         | uuid                 |                                                                   |
| `contractId` | uuid                 |                                                                   |
| `period`     | `YYYY-MM`            | **месяц договора**, за который поставлен статус — обязателен      |
| `status`     | `awaiting` \| `paid` | на какой статус переключили                                       |
| `createdAt`  | datetime             | дату и время выбирает пользователь — можно оформить задним числом |
| `by`         | string               | кто переключил (имя пользователя из сессии)                       |

Меняет статус только admin — в поповере у карточки «Статус» рядом с «Бюджет / Прибыль».
Поповер состоит из двух вкладок: «Статус» (выбор статуса, дата смены и месяц) и «История».
Месяц и дата связаны: выбрали апрель — дата уезжает в апрель, поправили дату руками —
подсветится её месяц.

Сохранение обновляет три вещи: `paymentStatusByPeriod[period]`, пару
`paymentStatus`/`paymentStatusAt` (последняя по времени смена) и дописывает запись в
`paymentLog`. `paymentStatusAt` не равен `paymentLog[0].createdAt`, если смену оформили
задним числом.

**Зачем месяц.** Статус красит вкладку месяца в фильтре: зелёная — `paid`, красная —
`awaiting`, у месяцев без статуса остаётся жёлтая шкала. Карточка «Статус» показывает статус
выбранного месяца, а если месяц не выбран — последний по времени.

## 3. Справочники

**Статусы кампании** (`src/lib/metrics.js`):

| Код                | Подпись         | Смысл                            |
| ------------------ | --------------- | -------------------------------- |
| `sent`             | Отправлен       | заявку создал рекламодатель      |
| `received`         | Получен         | площадка приняла в работу        |
| `reviewing`        | Рассматривается | на согласовании                  |
| `active`           | Активен         | идёт размещение                  |
| `completed`        | Завершен        | закончилась                      |
| `awaiting_payment` | Ожидает оплату  | отработала, деньги ещё не пришли |

Порядок в воронке — как в таблице; сортировка списка идёт по нему. `awaiting_payment` —
новый статус, идёт после «Завершен»; в интерфейсе выделен красным и пульсирует.

**Пакеты:** `partner` — Партнёр, `general` — Генеральный спонсор, `presenter` — Презентер.

**Лиги:** `epl`, `laliga`, `bundesliga`, `ligue1`, `seriea`, `ufc`, `f1`, `atp`, `wta`,
`zuffa`, `nba`, `nhl`.

**Статусы бренда:** `active`, `paused`. **Статусы площадки:** `active`, `inactive`.

## 4. Бизнес-правила

1. **Создание кампании.** Создаёт только рекламодатель, статус всегда `sent`. Обязательны
   название (оно же — рекламная кампания из договора) и период. Бюджет при создании = 0 —
   его проставляет площадка.
2. **Смена статуса.** Только admin, вручную, любым переходом (жёсткого автомата нет).
   Проверять, что статус из списка.
3. **Редактирование.** Admin правит кампанию в любом статусе, включая `active` и `completed`
   (ограничение снято). Рекламодатель после отправки заявку не редактирует.
4. **Удаление кампаний** в UI отключено, эндпоинт можно не делать.
5. **Договор.** При выборе номера договора в кампанию копируются пакет, лиги, юр. лицо и
   срок. Название кампании рекламодатель **вписывает сам** — это свободное поле, а не выбор
   из договора; под ним подсказка «В договоре указана: …» и автодополнение. Если введённое
   название совпало с `contract.campaignName`, в кампанию подставляется ролик договора
   (`creative` → `creativeUrl` / `creativeName` / `creativeAddedAt`). Дальше это снимок:
   правка договора не меняет существующие кампании. Если у бренда договоров нет — номер
   вводится вручную.
6. **Что рекламодатель не редактирует в форме кампании.** Срок договора подставляется из
   договора и заблокирован, поле юр. лица скрыто, файл договора доступен только на скачивание,
   подставленный ролик нельзя удалить (заменить своим — можно).
7. **Деньги — на договоре, а не на кампании.** `budget` — сколько бренд должен заплатить по
   договору, `spent` — сколько оплатил. Поступление вносится с суммой и датой-временем,
   прибавляется к `spent` и попадает в историю выплат. В историю пишется весь прирост
   `spent`, включая правку поля «Оплачено» руками (см. 2.8). Рекламодатель и viewer видят
   суммы и историю, но не правят их.
   7a. **Статус оплаты — по месяцам договора.** Два значения: `awaiting` («Ожидает оплату»,
   красный, пульсирует) и `paid` («Оплачено», зелёный). Admin выбирает статус, месяц
   (`period`) и дату-время смены — можно задним числом. Смена пишется в
   `paymentStatusByPeriod[period]` и в `paymentLog` вместе с автором. Вкладка месяца в
   фильтре красится по статусу этого месяца.
   7b. **Роли в договоре.** Рекламодатель правит только `campaignName` и `creative`; площадка —
   всё остальное. Наблюдатель не правит ничего.
8. **Уникальность номера договора** — по всей базе, а не только внутри бренда: иначе один
   номер всплывает у двух брендов и путает выбор в форме кампании.
9. **Удаление бренда** не удаляет его кампании — они остаются без привязки; UI
   предупреждает об этом.
10. **Счётчики.** На вкладках брендов показывается число кампаний, количество заявок в
    статусе `sent` (синяя метка) и количество активных (зелёная). Вкладки статусов с нулевым
    счётчиком в фильтрах не показываются.
11. **Процент на статусе** — это доля пройденного срока кампании
    (`timeProgress` в `src/lib/metrics.js`), а не освоение бюджета. Освоение показывает
    полоса на карточке договора «Бюджет / Прибыль» — `spent / budget`.
12. **Что не отдавать наблюдателю.** Роль `viewer` не должна видеть просмотры: колонку
    «Просмотры» в медиаплане (и её сумму в итогах), метрику «TV Live Ads Views» в Spot
    statistic, а в Total statistics — «Просмотры Live Ads», «Распределение устройств» и
    «География аудитории». Сейчас фронт их прячет; в API эти поля тоже лучше не отдавать.

## 5. API

Базовый префикс `/api/v1`. Ответы — JSON, ошибки — `{ "error": { "code", "message", "fields": {} } }`.

### Аутентификация

```
POST   /auth/login          { login, password } → { token, user }
POST   /auth/logout
GET    /auth/me             → { user }
```

`user` — `{ id, role, name, email, advertiserId }`.

### Рекламодатели

```
GET    /advertisers                    (admin) список с contracts и requisites
POST   /advertisers                    (admin)
GET    /advertisers/:id
PATCH  /advertisers/:id                (admin)
DELETE /advertisers/:id                (admin)
```

Договоры приходят и сохраняются вместе с брендом (форма правит их одним списком).
Если удобнее — отдельные `POST/PATCH/DELETE /advertisers/:id/contracts/:contractId`,
фронт подстроится.

### Площадки

```
GET    /channels
POST   /channels                       (admin)
PATCH  /channels/:id                   (admin)
DELETE /channels/:id                   (admin)
```

### Кампании

```
GET    /campaigns?advertiserId=&status=&contractNumber=&q=
GET    /campaigns/:id
POST   /campaigns                      (advertiser)
PATCH  /campaigns/:id                  (admin)
```

Для роли `advertiser` сервер сам ограничивает выдачу его брендом, независимо от параметров.

### Договоры: деньги и статус оплаты

Деньги переехали с кампании на договор, поэтому эндпоинты — по договору:

```
PATCH  /contracts/:id/amounts            (admin) { budget?, spent? }
GET    /contracts/:id/payments            история выплат, все роли
POST   /contracts/:id/payments           (admin) { amount, paidAt }
PATCH  /contracts/:id/payments/:payId    (admin) { paidAt?, amount?, comment? }
DELETE /contracts/:id/payments/:payId    (admin) удаляет поступление, `spent` уменьшается
GET    /contracts/:id/status-log          история смен статуса, все роли
PUT    /contracts/:id/payment-status      (admin) { status, period, changedAt }
PATCH  /contracts/:id/campaign-info       (advertiser) { campaignName?, creative? }
```

Поступление прибавляется к `spent`, дату и время задаёт пользователь; любой прирост `spent`
(в том числе правкой поля «Оплачено») создаёт запись в истории. Ответ — обновлённый договор
вместе с историей. Правка даты уже внесённой выплаты нужна: в интерфейсе она редактируется
прямо в списке.

`PUT /payment-status` принимает месяц (`period` вида `2026-08`) и возвращает договор с
обновлённым `paymentStatusByPeriod[period]`, парой `paymentStatus`/`paymentStatusAt` и
дописанной записью `paymentLog` (`{ period, status, createdAt: changedAt, by }`).
`changedAt` может быть в прошлом. Записи без `period` — формат старой версии, фронт их
выбрасывает при загрузке.

`PATCH /campaign-info` — единственный договорный эндпоинт, доступный рекламодателю: только
своей брендовой записи и только эти два поля.

### Медиаплан и логи выходов

```
GET    /campaigns/:id/media-plan/:tab           tab = spot1 | spot2
PUT    /campaigns/:id/media-plan/:tab           { rows: [...] }   (admin) — сохранение целиком
GET    /campaigns/:id/logs/:tab                 tab = ss1uzb | ss2uzb | promo1 | promo2
PUT    /campaigns/:id/logs/:tab                 { rows: [...] }   (admin)
```

Фронт правит таблицу целиком и сохраняет по кнопке — `PUT` со всем списком строк
проще всего и совпадает с текущим поведением.

### Файлы

```
POST   /files                          multipart → { id, name, url, size, mime }
```

Используется для скана договора, рекламного ролика и логотипа бренда. В сущностях храним
`{ name, url }`, у бренда — только `url`.

### Аналитика

```
GET    /campaigns/:id/timeseries?metric=spent|impressions|clicks&days=14
GET    /campaigns/:id/report                    сводка по каналам, гео, устройствам, соцсетям
GET    /overview                                (admin) сводка для страницы «Обзор»
GET    /reports/summary                         (advertiser) для страницы «Отчёт»
```

## 6. Файлы

- Сейчас файлы кладутся в базу как `data:`-URL с лимитом 2 МБ, крупные держатся
  на `blob:`-ссылке до перезагрузки. Это заглушка.
- Нужно: загрузка в S3-совместимое хранилище, отдача по ссылке, ограничение типов
  (`.pdf/.doc/.docx/изображения` для договора, `video/*` для ролика, `image/*` для логотипа)
  и размера.
- Вместе с файлом сохраняется **дата и время загрузки** (`addedAt`): фронт показывает
  «Добавлен 18.08.2026 23:53» у скана договора, ролика договора и ролика кампании.
  Проставляет сервер в момент загрузки; при замене файла обновляется.
- Ссылка на ролик может быть и внешней (`http(s)`) — фронт это допускает.
- Скачивание: договор качается из карточки кампании (плитка «Номер договора»), из формы
  договора и из формы кампании у рекламодателя; ролик — из формы договора. Ссылка должна
  отдаваться с именем файла, чтобы `download` сохранял его читаемо.

## 7. Импорт и экспорт Excel

Разбор и сборка `.xlsx` сейчас делаются на клиенте (`src/lib/xlsx.js`, зависимость `fflate`).
Если оставляем так — от бэкенда нужно только сохранение строк. Если переносим на сервер —
вот что должен уметь парсер.

**Медиаплан (Live Spot).** Заголовки распознаются по названиям: `Дата`, `Время GMT+4`,
`Турнир`, `Событие`, `Канал`, `Pre`, `Mid 1`, `Mid 2`, `Post`, `Просмотры` (и англоварианты).
Если строки заголовков нет — колонки читаются по порядку. Пустые строки отбрасываются.

**Логи выходов.** Клиент присылает один файл на месяц — «Шаблон импортируемого отчёта
Setanta Statistics». В нём семь листов, вкладки берут свои:

| Вкладка             | Лист в шаблоне                                 |
| ------------------- | ---------------------------------------------- |
| `ss1uzb`            | `2.1) SS1 UZB TV`                              |
| `ss2uzb`            | `2.2) SS2 UZB TV`                              |
| `promo1`            | `3.1) Event Promo SS 1`                        |
| `promo2`            | `3.2) Event Promo SS2`                         |
| медиаплан Live spot | `1.1) Live Events SS1`, `1.2) Live Events SS2` |
| соцсети             | `4.1) Social Media` (ссылка + Impressions)     |

Имя листа сопоставляется без учёта пробелов и регистра. Шапка файла (название бренда,
пустые строки) пропускается, данные читаются после строки `ITEM NAME | DATE | TIME`.

**Форматы значений.** В одних листах время текстом (`19:09:13`), в других — числом-долей
суток (`0.578136…` → `13:52:31`). Даты могут прийти порядковым номером дня Excel
(отсчёт от 30.12.1899) — разворачиваются в `дд.мм.гггг`.

**Экспорт.** Кнопка «Скачать» собирает `.xlsx` из текущей таблицы (лист называется как
вкладка, первая строка — заголовки).

**Фикстуры для дева.** Демо-логи лежат в `src/lib/spotLogSeed.js`: Standart spot — первые
50 строк листа `2.1) SS1 UZB TV`, Event promo — 47 строк промо-выгрузки; SS2 в обоих случаях
повторяет SS1. Они подставляются только в пустую вкладку и не затирают импортированное.
Медиаплан Live Spot берётся из `src/lib/liveSpotSeed.js`.

## 8. Метрики

Формулы уже зафиксированы в `src/lib/metrics.js`, повторить один в один:

```
ctr    = impressions ? clicks / impressions * 100 : 0
cvr    = clicks ? conversions / clicks * 100 : 0
cpa    = conversions ? spent / conversions : 0
cpm    = impressions ? spent / impressions * 1000 : 0
pacing = budget ? spent / budget * 100 : 0
```

Агрегаты по списку кампаний: суммы `budget`, `spent`, `impressions`, `clicks`,
`conversions`, плюс `ctr`, `cvr`, `cpa` от сумм и количество активных.

**Что сейчас захардкожено во фронте и должно приехать с бэка:**

- страница «Обзор» — `src/pages/Dashboard.jsx` (медиапоказатели, соцсети, гео, устройства);
- отчётные панели кампании — `src/components/campaigns/CampaignReportPanels.jsx`
  (Total Spot statistic, Social media, Total statistics, список городов);
- графики динамики на странице статистики — генерируются функцией `seededSeries`
  (`src/lib/id.js`), то есть это псевдослучайные числа, а не данные.

### 8.1 Отчёт за закрытый месяц

Когда в фильтре выбран **закрытый** месяц, вместо таблицы кампаний открывается отчёт
(`src/components/campaigns/MediaReport.jsx`, вкладки — `CampaignMediaTabs.jsx`).
Заголовок: «Статистика за <месяц> <год>».

**Состав вкладок собирает площадка, и он свой у каждого договора.** Жёстко зашита только
группа STATISTIC с вкладками `Spot` (сводка по каналам) и `Total` (общая статистика).
Остальное добавляется кнопкой «+»: категория выбирается **из фиксированного списка**,
названий руками не вводят, и приходит сразу со своими каналами.

| Категория     | Каналы (id)                                            | Тип таблицы |
| ------------- | ------------------------------------------------------ | ----------- |
| Live spot     | Setanta Sports 1 (`spot1`), Setanta Sports 2 (`spot2`) | `plan`      |
| Standart spot | SS1 (`ss1uzb`), SS2 (`ss2uzb`)                         | `log`       |
| Event promo   | SS1 (`promo1`), SS2 (`promo2`)                         | `log`       |
| Social media  | Instagram (`social_ig`), Telegram (`social_tg`)        | `social`    |
| OTT           | Live spot (`ott_live`), Preroll (`ott_preroll`)        | `log`       |

| Тип                 | Что открывается                         |
| ------------------- | --------------------------------------- |
| `plan` — медиаплан  | редактируемый медиаплан Live Spot (2.6) |
| `log` — лог выходов | таблица выходов роликов (2.7)           |
| `social` — соцсеть  | отчёт публикаций и показов (см. ниже)   |

Категорию можно **убрать**: карандаш рядом с «+» включает режим правки, у категорий
появляется крестик, удаление спрашивает подтверждение и показывает тост. Постоянная
STATISTIC не удаляется. Данные удалённой категории не трогаются — при повторном добавлении
таблицы возвращаются.

Модель для бэка:

| Сущность       | Поля                                                                          |
| -------------- | ----------------------------------------------------------------------------- |
| ReportCategory | `id`, `contractId`, `name`, `position`                                        |
| ReportChannel  | `id`, `categoryId`, `label`, `kind` (`plan` \| `log` \| `social`), `position` |

```
GET    /contracts/:id/report-tabs                (все роли) категории с каналами
POST   /contracts/:id/report-categories          (admin) { name } — имя из списка выше,
                                                 сервер сам заводит её каналы
DELETE /report-categories/:id                    (admin) вместе с каналами; строки таблиц
                                                 сохраняются
```

Медиаплан и логи привязываются к каналу (`channelId`), а не к жёстко заданной вкладке:
эндпоинты из §5 принимают `channelId` вместо `tab`. Во фронте состав вкладок пока лежит
в `localStorage` под ключом `setanta.campaign.custom-tabs.v2`, разложенный по договорам;
у демо-договора Д-2026/102 он отдаётся заполненным.

**Итоги медиаплана.** Под таблицей Live Spot — строка «Итого»: слева количество размещений
и вставок (`строк` и `строк × 4`), затем **суммы по числовым колонкам**: `pre`, `mid1`,
`mid2`, `post` (хронометраж, секунды) и `views` (просмотры, подписаны отдельно «Итого
просмотров»). Второй строкой — «Сумма секунд»: `pre + mid1 + mid2 + post` за весь период. Сейчас фронт считает их из строк таблицы; на бэке удобнее отдавать готовые
агрегаты вместе с медиапланом:

```
GET /campaigns/:id/media-plan/:tab → { rows: [...], totals: { pre, mid1, mid2, post, views, rows, spots } }
```

**Ограничения роли `viewer`** (см. правило 12): колонки `views` и её суммы в ответе быть
не должно; в `Spot` — без `TV Live Ads Views`; в `Total` — без «Просмотры Live Ads»,
устройств и географии. Собирать вкладки и править сводки может только admin.

### 8.1.1 Сводки и соцсети редактируются вручную

Раньше `Spot`, `Total` и отчёты соцсетей были картинкой из констант. Теперь у каждой панели
есть режим правки (кнопка «Редактировать» → «Сохранить» / «Отмена», тост после сохранения),
и все цифры вводятся руками. В полях число сразу разделяется по разрядам: `14 111 352`.

| Панель             | Что правится                                                                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Spot`             | названия каналов; Standard spot (ролики и секунды), Live spot UFC / Football (Live Ads и секунды), TV Live Ads Views; TV Event Promo Count и OTT Pre-roll Views                                        |
| `Total`            | пять метрик сводки; Posts и Impressions по каждой соцсети; распределение устройств (название и доля, диаграмма пересчитывается); география аудитории — город и процент, строки добавляются и удаляются |
| соцсеть (`social`) | ссылки публикаций и показы построчно, строки добавляются и удаляются; отдельно «Публикации» и «Impressions» — они ведутся руками и не обязаны быть суммой строк                                        |

Для бэка это значит: сводки — не только вычисляемые данные, но и сохраняемые сущности.

```
GET  /contracts/:id/report-stats/:panel     panel = spot | total   (все роли)
PUT  /contracts/:id/report-stats/:panel     (admin) — панель целиком
GET  /report-channels/:id/social            (все роли) { posts, impressions, rows[] }
PUT  /report-channels/:id/social            (admin) — { posts, impressions, rows[] }
```

`rows[]` соцсети: `{ id, link, views, position }`. Во фронте это `localStorage`:
`setanta.campaign.report-stats.v1` (панели `spot` и `total`) и
`setanta.campaign.social.v1` (по каналу). Сохранённая панель склеивается с эталонным
набором — записи старого формата не должны ронять экран, если в API добавится новый блок.

Значения по умолчанию (демо-данные) лежат в
`src/components/campaigns/CampaignReportPanels.jsx`; при переносе их удобно взять как
фикстуры.

### 8.2 Страница «Отчёт» рекламодателя

## 9. На что обратить внимание при переносе

1. **`createdAt` с временем.** Подсказка на статусе показывает дату и время отправки заявки —
   если сохранять только дату, время пропадёт.
2. **Формат дат.** Фронт везде выводит `дд.мм.гггг`, API удобнее отдавать ISO (`2026-08-31`)
   и `datetime` в ISO 8601 — форматирование на клиенте.
3. **Числа** передавать числами, не строками: суммы, охваты, метрики.
4. **Порядок строк** в медиаплане и логах важен — либо сохранять `position`, либо
   гарантировать порядок массива.
5. **Миграции в `src/lib/store.js`** (донабивка юр. лиц, договоров, статусов) — костыли мока,
   переносить не нужно.
6. **Точки интеграции на фронте:** `src/lib/store.js` и `src/context/DataContext.jsx` —
   там сейчас `create / update / remove / getState / subscribe`. Достаточно заменить их
   реализацию на HTTP-вызовы, компоненты трогать не придётся.

## 10. Что заложить в архитектуру сразу

Это не фичи, а решения, которые дорого менять потом.

**Пагинация и сортировка.** Кампаний будет сотни, строк логов — тысячи (месяц выходов
на четыре вкладки ≈ 2400 строк). Договориться о формате сразу:

```
GET /campaigns?limit=50&cursor=...&sort=-createdAt
→ { "items": [...], "nextCursor": "...", "total": 128 }
```

**Конкурентная правка.** Суммы кампании правит площадка, статус — тоже; два менеджера
легко перетрут друг друга. Нужна оптимистичная блокировка: отдавать `version` (или
`updatedAt`) и отклонять `PATCH` со старым значением, чтобы фронт показал «данные
изменились, обновите».

**Идемпотентность платежей.** «Поступление» прибавляет сумму — повторный запрос при
разрыве связи задвоит деньги. Принимать `Idempotency-Key` и игнорировать повтор.

**Аудит.** Кто менял статус, суммы, условия договора — писать в отдельную таблицу
(`entity`, `entityId`, `field`, `old`, `new`, `userId`, `at`). Для денег и договоров это
обязательное требование, а не удобство.

**Мягкое удаление.** Бренд удаляется, а его кампании остаются — при жёстком `DELETE`
история платежей и отчёты повиснут на несуществующем `advertiserId`. Лучше `deletedAt`.

**Формат ошибок и валидации.** Фронт умеет показывать ошибки под конкретными полями —
возвращать `{ error: { code, message, fields: { name: "Укажите название" } } }`, а не
просто 400.

**Хранение денег.** Суммы в узбекских сумах доходят до сотен миллионов — целые числа
(минорные единицы) или `numeric`, не `float`.

**Часовые пояса.** Медиаплан подписан «Время GMT+4» — хранить `timestamptz`, а не
локальные строки, иначе выходы поедут.

**i18n-готовность.** Справочники (статусы, пакеты, лиги, категории) отдавать кодами,
подписи держать на клиенте — иначе перевод на узбекский упрётся в базу.

### 11.1 Акт сверки по бренду

История выплат на фронте уже есть (см. 2.8), но только внутри кампании. Для бухгалтерии
нужен свод по бренду и договору:

```
GET /advertisers/:id/payments?contractNumber=&from=&to=
```

Плюс поля, которых во фронте пока нет и которые дешевле завести сразу:
`comment`, `createdBy` (кто внёс), привязка к `contractNumber`.

### 11.2 Статистика из загруженных логов

Самое ценное по соотношению польза/затраты: клиент **уже** грузит реальные выходы в
`SS1/SS2 UZB` и `Event Promo`, а «Total statistics» и графики нарисованы константами.

Из строк лога (`item`, `date`, `time`) считаются: количество выходов за период,
разбивка по дням и по каналам, хронометраж (из медиаплана — `pre/mid1/mid2/post`),
просмотры. Эндпоинты `/campaigns/:id/timeseries` и `/campaigns/:id/report` из раздела 5
должны отдавать именно это, а не заглушки.

### 11.3 Уведомления

Событий уже хватает: пришла заявка (`sent`), сменился статус, приближается `paymentDate`,
заканчивается договор или период кампании.

```
Notification: id, userId, type, payload, readAt, createdAt
GET   /notifications?unread=true
POST  /notifications/:id/read
```

Плюс доставка наружу — email и/или Telegram. Колокольчик в шапке фронта пока декоративный,
под это и делался.

### 11.4 Комментарии к кампании

Сейчас после отправки заявки диалога нет: площадка не может попросить заменить ролик,
рекламодатель — уточнить статус. Всё уходит в мессенджеры.

```
Comment: id, campaignId, authorId, text, attachments[], createdAt
GET/POST /campaigns/:id/comments
```

Хорошо ложится вместе с аудитом: смена статуса пишется в ту же ленту системным сообщением.

### 11.5 Несколько пользователей на бренд

Один логин на компанию — это пароль, который пересылают в чате. Нужны связь
`user ↔ advertiser` многие-к-одному, приглашение по email, сброс пароля, отзыв доступа.

### 11.6 Дубликат кампании

`POST /campaigns/:id/duplicate` — копия с новым `id`, статусом `sent`, обнулёнными
метриками и суммами. Кампании повторяются сезонно, а форма длинная.

### 11.7 Сборка отчёта одним файлом

`GET /campaigns/:id/report.xlsx` — медиаплан, логи выходов и итоги в одной книге.
Рекламодателю есть что переслать своему клиенту. Экспорт из отдельных таблиц на фронте
уже написан (`src/lib/xlsx.js`), серверная сборка нужна для «всё сразу» и для писем.

### 11.8 Связность данных

Проверки, которых на сервере пока нет:

- номер договора уникален по всей базе (на фронте проверка уже есть, но она клиентская);
- период кампании укладывается в срок выбранного договора;
- `paymentDate` не раньше начала кампании;
- сумма поступлений не превышает `budget` (или явное разрешение переплаты);
- нельзя удалить договор, на который ссылаются кампании (или отвязывать явно).

## 12. Открытые вопросы

1. **Комментарий и автор у поступления.** В UI вносятся только сумма и дата — нужны ли
   комментарий и `createdBy` для акта сверки? (Привязка к договору уже есть — поступления
   переехали в договор, см. 2.8. У смены статуса автор пишется, у поступления — пока нет.)
2. **Переход в `awaiting_payment`** — ставится вручную или автоматически, когда кампания
   завершилась, а `spent < budget`?
3. **Смена статуса кампании** — свободные переходы или строгий автомат
   (`sent → received → reviewing → active → completed → awaiting_payment`)?
4. **Права рекламодателя на правку.** Сейчас после отправки он не может изменить заявку —
   оставляем так или разрешаем правку, пока статус `sent`?
5. **Площадки (`/app/channels`)** скрыты из меню, но страница работает. Нужны ли они в проде?
6. **Категории брендов** — фиксированный справочник или произвольный текст?
7. **Медиапланы и логи** — хранить по кампании (как предложено) или по договору/месяцу?
   Сейчас фронт показывает их как отчёт за выбранный месяц договора, см. §13.
8. **Реквизиты бренда** — оставляем свободным текстом или возвращаем структуру полей
   (ИНН, банк, счёт), чтобы подставлять их в документы?
9. **Несколько рекламных кампаний на договор.** Сейчас в договоре одно поле `campaignName`,
   которое заполняет рекламодатель, а в форме кампании название вводится свободно. Если
   кампаний по договору бывает несколько — в договоре нужен список, а не строка.
10. **Статус оплаты и суммы.** Ставить `paid` вручную (как сейчас) или автоматически, когда
    `spent >= budget`? И нужна ли блокировка смены статуса задним числом раньше даты договора?
11. **Мультиязычность** интерфейса — сейчас только русский, влияет на формат дат и подписи.

## 13. Навигация по кампаниям — что за фильтры на экране

Порядок фильтров: **бренд → договор → месяц**. Это влияет на то, какие выборки нужны с сервера.

- **Вкладки брендов** — только бренды, у которых есть кампании; счётчики: всего, новых
  заявок (`sent`), активных.
- **Вкладки договоров** появляются, когда выбран бренд; счётчик — число кампаний по договору.
  Повторный клик снимает фильтр. Смена бренда сбрасывает выбранный договор и период.
- **Месяцы** появляются, когда выбран договор. Месяц отбирает кампании, чей период
  пересекается с ним; будущие месяцы недоступны.
  - **текущий месяц** — показывается таблица кампаний;
  - **закрытый месяц** — вместо таблицы открывается отчёт (медиаплан и логи выходов).
- **Статусы** — сегментные вкладки со счётчиками; вкладки с нулём скрываются.
- Рядом с выбранным договором показываются: кнопки «Открыть договор» и «Скачать договор»
  (файл договора), карточка «Бюджет / Прибыль» (суммы и история выплат) и карточка
  «Статус» (статус оплаты, дата последней смены). Колонки «Номер договора» и «Бюджет»
  из таблицы кампаний убраны — договор теперь выбирается вкладками выше.

Для сервера это означает как минимум фильтры `advertiserId`, `contractNumber`,
`period` (месяц/диапазон) и агрегаты для счётчиков — лучше отдавать их отдельным
эндпоинтом (`GET /campaigns/facets?...`), чтобы не тянуть весь список ради цифр.

## 14. Что изменилось со времени прошлой версии документа

Дата: 19.08.2026. Правки фронта, которые затрагивают бэкенд.

**Деньги переехали с кампании на договор**

- `contract.budget`, `contract.spent`, `contract.payments` — вместо одноимённых полей кампании
  (в кампании они остались только для старых записей и в UI не используются).
- В историю выплат пишется **любой прирост** `spent`, включая правку поля «Оплачено» руками:
  первая оплата, вбитая прямо в «Оплачено», раньше в историю не попадала.
- Эндпоинты сумм и выплат — по договору: `/contracts/:id/amounts`, `/contracts/:id/payments`.

**Статус оплаты договора — по месяцам (новое)**

- `contract.paymentStatusByPeriod` = `{ 'YYYY-MM': { status, changedAt } }` — основное
  хранилище; `paymentStatus` / `paymentStatusAt` остались как «последняя смена».
- `contract.paymentLog[]` = `{ id, period, status, createdAt, by }` — записи без `period`
  (формат первой версии) фронт удаляет при загрузке.
- Меняет только admin; месяц, дату и время выбирает пользователь, можно задним числом.
- Вкладка месяца в фильтре красится по статусу: зелёная — оплачен, красная — ждём оплату.
- Эндпоинты: `PUT /contracts/:id/payment-status` (`{ status, period, changedAt }`),
  `GET /contracts/:id/status-log`.

**Дата загрузки файлов (новое)**

- `file.addedAt` и `creative.addedAt` у договора, `campaign.creativeAddedAt` у кампании.
- Показывается подписью «Добавлен дд.мм.гггг чч:мм» в форме загрузки, в карточке договора,
  в справке «От рекламодателя» и на плитке «Ролик» в карточке кампании.
- Если у кампании даты нет, фронт берёт её из ролика договора — но только при совпадении ссылки.

**Кто что заполняет в договоре**

- У админа из формы договора убраны «Название рекламной кампании» и «Рекламный ролик»
  (и в карточке договора, и в карточке бренда) — вместо них справка «От рекламодателя».
- Рекламодатель эти два поля теперь **редактирует** у себя в карточке договора и сохраняет.
- Сервер должен ограничить запись: рекламодателю — только `campaignName` и `creative`
  своего бренда (`PATCH /contracts/:id/campaign-info`).

**Форма кампании**

- «Рекламная кампания» — свободное поле ввода вместо выпадающего списка из договора.
  Название из договора остаётся подсказкой и автодополнением; при совпадении подтягивается
  ролик договора вместе с `creativeAddedAt`.

**Отчёт за месяц**

- Под таблицей медиаплана — строка «Итого» с суммами по `pre`, `mid1`, `mid2`, `post` и
  `views` (раньше там стояло количество строк). Просмотры подписаны отдельно.
  Удобно отдавать готовые `totals` вместе с `rows` (см. 8.1).
- Вкладки отчёта сгруппированы: LIVE SPOT / UZB TV / EVENT PROMO и сводные
  (Spot statistic, Social media, Total statistics).
- Страница «Отчёт» рекламодателя (`/app/reports`) — сводка Total statistics по бренду,
  `GET /reports/summary`, заложить `?from=&to=`.

**Роль `viewer`: скрыты просмотры**

- Нет колонки «Просмотры» в медиаплане и её суммы в итогах.
- Нет метрики «TV Live Ads Views» в Spot statistic.
- В Total statistics нет «Просмотры Live Ads», «Распределение устройств» и «География аудитории».
- Эти поля лучше не отдавать и в API (правило 12).

**Таблица кампаний**

- Убраны колонки «Бюджет / Прибыль» (переехала на договор) и «Номер договора» (договор
  выбирается вкладками). Сортировки и фильтры не менялись.

**Не влияет на бэкенд, для полноты:** новые локальные шрифты (Setantica 2023 + Noto Sans,
`public/fonts`), красный крестик сброса месяца, подсказки на кнопках договора, подсветка
активной группы во вкладках отчёта, демо-даты загрузки роликов и демо-статусы оплаты по
месяцам в `src/lib/seed.js` (январь–май 2026 — «Оплачено», дальше чередование до августа).

**Вкладки отчёта собирает пользователь (новое, 20.08.2026)**

- Зашитых групп LIVE SPOT / STANDART SPOT / EVENT PROMO / SOCIAL MEDIA больше нет.
  Постоянная только группа STATISTIC (`Spot`, `Total`).
- Кнопка «+» в ленте вкладок: сначала категория, потом каналы внутри неё; у канала
