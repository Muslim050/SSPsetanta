# Бэкенд: состояние API и что нужно фронту

Стенд `https://setanta.pythonanywhere.com`, схема `/api/v1/schema`, фронт —
ветка `dev`. Каждый пункт проверен запросом; ответ сервера приведён.
Состояние на 22.09.2026: из раздела 3 закрыто тринадцать пунктов из
девятнадцати, открытое собрано в начале раздела.

Раздел «Площадки» (`/channels`) сознательно не трогаем: эндпоинты есть, экран
живёт на моке, подключим позже.

---

## 1. Что подключено

| Раздел      | Эндпоинты                                                                                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| auth        | `login`, `logout`, `me`, `refresh` — с прозрачным обновлением истёкшего access                                                                                                  |
| advertisers | список, создание, карточка, `PATCH`, удаление, смена статуса из плитки, логотип файлом (`logoId`), `campaignsCount`                                                             |
| contracts   | `POST`/`PATCH`/`DELETE` внутри бренда, `PATCH /contracts/:id`, `amounts`, `payment-status`, `campaign-info`, правка и удаление поступлений                                      |
| campaigns   | список, создание (рекламодателем), `PATCH`, ролик файлом (`creativeId`)                                                                                                         |
| users       | список, создание, `PATCH`, удаление                                                                                                                                             |
| files       | `POST /files` для скана договора, ролика и логотипа бренда; файл отдаётся по слагу без авторизации — ссылка идёт прямо в `<img>` и `<a download>`                               |
| reports     | месяцы с отчётом, отчёт за месяц, импорт файла, сохранение листа с `version` и 409, выгрузка в `.xlsx` — по [reports-api.md](reports-api.md); на стенде пока не выкачены (3.24) |

Кроме `channels`, в схеме не осталось неподключённых разделов. История
загрузок отчёта (`GET …/reports/imports`) открывается у площадки кнопкой
«История» в плашке файла.

## 3. Задачи бэкенду

Закрытые пункты зачёркнуты и сжаты до строки с подтверждением — нумерация
сохранена, на неё ссылаются соседние документы и комментарии в коде.
Открытыми остались 3.1, 3.9, 3.12, 3.14, 3.18, 3.19, четыре пункта про файлы —
3.20–3.23, они всплыли, когда фронт переходил на загрузку файлов, — и два
про отчёт за месяц: 3.24 и 3.25.

### Блокирующее

#### 3.1 CORS: в белом списке чужой порт

Заголовки появились, но пускают не нас. Preflight с нашими origin'ами
(22.09):

```
Origin: http://localhost:5178            → Access-Control-Allow-Origin нет
Origin: https://setantadev.vercel.app    → Access-Control-Allow-Origin нет
Origin: http://localhost:5173            → Access-Control-Allow-Origin: http://localhost:5173
```

`5173` — дефолтный порт Vite, наш дев поднимается на **5178**
(`vite.config.js`). Пока список такой, фронт по-прежнему ходит через прокси
(`server.proxy` в разработке, `rewrites` на Vercel), и любой сторонний клиент
упрётся в то же самое.

**Нужно:** добавить в белый список `http://localhost:5178` и
`https://setantadev.vercel.app`.

### Файлы

#### 3.2 ~~Скачивание закрыто токеном~~

**Сделано.** `GET /files/<slug>/download` без `Authorization` → `200`.
Ссылка идёт прямо в `<img src>` и `<a download>`, блоб-обход убран.

#### 3.3 ~~`logoId` у бренда~~

**Сделано.** `logoId` на запись, `logoFile` на чтение. Проверено:
`PATCH /advertisers/12 {"logoId":19}` → в ответе `logoFile`, `logoId:null` убирает.

#### 3.4 ~~`creativeId` у кампании~~

**Сделано.** `creativeId` на запись, `creative` на чтение; `creativeName`
и `creativeAddedAt` сервер заполняет из файла сам. Ссылку в `creativeUrl`
фронт больше не кладёт — см. 3.22 про старые записи.

#### 3.5 ~~`Upload.file` описан как `uri`~~

**Сделано.** В схеме `type: string, format: binary`.

### Пользователи

#### 3.6 ~~Имя, фамилия и телефон~~

**Сделано.** `firstName`, `lastName`, `phone` есть в выдаче и на запись,
`name` собирает сервер. Фронт переходит на них во втором заходе.

### Договоры

#### 3.7 ~~В договоре нет `advertiserId`~~

**Сделано.** `GET /contracts` отдаёт `advertiserId`.

#### 3.8 ~~`GET /contracts` не похож на остальные списки~~

**Сделано.** `{items, nextCursor, total}` плюс `limit`, `cursor`,
`q`, `status`, `advertiserId`.

#### 3.9 Номер договора не уникален

Спека (§2.3): «`number` — уникален по всей базе». Фактически
`POST /advertisers/3/contracts {"number":"Д-2026/1001"}` → `201`, хотя номер
уже был у другого бренда. Кампания ссылается на договор по номеру — дубликаты
делают выбор неоднозначным.

**Нужно:** `unique` на номер и `400` с полем `number` в `fields`.

Перепроверить со стороны фронта нечем: дубликат пришлось бы создать, а
плодить мусор на стенде не хочется. Подтвердите словами, что ограничение
навесили.

#### 3.10 ~~`paymentStatus` пустой строкой~~

**Сделано.** `oneOf: PaymentStatusEnum + BlankEnum`, `nullable`.

#### 3.11 ~~`leagues` без типа~~

**Сделано.** `type: array, items: string`.

### Кампании

#### 3.12 Заявка за бренд: описание и схема расходятся

Сценарий описан — в `CampaignCreate` появился текст «площадка `advertiserId`
присылает обязательно, без него `400`, статус будет `received`». Но само поле
в схеме осталось `readOnly: true`, то есть генераторы клиентов его не
отправят, а по схеме выходит, что отправлять и нельзя.

**Нужно:** снять `readOnly` с `advertiserId` в `CampaignCreate`. Как только
поле станет записываемым, включим у админа кнопку создания заявки.

### Общее

#### 3.13 ~~Снимок условий договора у кампании пустой~~

**Сделано.** Пакет, лиги, юр. лицо и срок приходят заполненными —
проверено на 39 кампаниях из 40 на странице (у сороковой нет договора).

#### 3.14 `version` и 409

Проверка работает, но только если поле прислать:

```
PATCH /advertisers/3 {"contact":"…","version":1} → 200, повторно → 409
PATCH /advertisers/3 {"contact":"…"}             → 200, без проверки
```

В схеме у `PATCH` только `200`. **Нужно:** описать `409` и решить, обязателен
ли `version`. Фронт его пока не шлёт — см. раздел 5.

#### 3.15 ~~Выйти с истёкшим access нельзя~~

**Сделано.** `POST /auth/logout` без `Authorization` → `204`.

#### 3.16 ~~Ошибки JWT нарушают собственный контракт~~

**Сделано.** `{"code":"unauthorized","message":"Сессия истекла, войдите заново","fields":{}}`.

#### 3.17 ~~`campaignsCount` у бренда и поиск `?q`~~

**Сделано.** `campaignsCount` в `Advertiser`, `?q` фильтрует список брендов.

#### 3.18 Порядок выдачи не описан

Списки идут, судя по всему, по убыванию `createdAt`, но в схеме ни слова и
параметра `sort` нет. Зафиксировать хотя бы в описании — от порядка зависит
стабильность курсорной пагинации.

#### 3.19 У `admin` пустые `name` и `email`

Мелочь: в шапке показывать нечего, фронт подставляет название роли.

### Всплыло при подключении файлов

#### 3.20 Ролик скачивается вместо просмотра

Хранилище отдаёт всё с `Content-Disposition: attachment`. Для скана договора
это правильно, для ролика — нет: кнопка «Посмотреть ролик» и плитка «Ролик»
в карточке кампании должны открывать видео во вкладке, а браузер вместо
этого начинает скачивание.

**Нужно:** `inline` для `video/*` и `image/*` — либо по типу файла, либо по
параметру `?inline=1`.

#### 3.21 У `AttachedFile` нет `id`

Ролик договора приходит как `{name, url, addedAt}` — без идентификатора
файла. Когда рекламодатель заводит заявку по договору, ролик переносится в
кампанию, и перенести его по `creativeId` нечем: приходится класть ссылку в
`creativeUrl`. Получается, что у половины кампаний ролик связан файлом, у
половины — строкой.

**Нужно:** `id` в `AttachedFile` (у `file`, `creative`, `logoFile`).

#### 3.22 Старые `creativeUrl` указывают на чужой origin

Пока у кампании не было `creativeId`, фронт складывал в `creativeUrl`
абсолютную ссылку — и origin туда попадал тот, с которого работал человек:

```
GET /campaigns/154 → creativeUrl: "https://setantadev.vercel.app/api/v1/files/…"
GET /campaigns/153 → creativeUrl: "http://localhost:5178/api/v1/files/…"
```

Вторая ссылка не откроется ни у кого, кроме автора. Новые записи так больше
не сохраняются.

**Нужно:** разово перенести такие ссылки в `creativeId` — слаг в адресе есть,
файл по нему находится.

#### 3.23 Загруженный файл нельзя удалить

`DELETE /files/:id` в схеме нет. Файл, который отвязали от сущности
(`logoId: null`, `creativeId: null`), остаётся в хранилище навсегда. Не
срочно, но со временем это мусор — особенно на роликах.

### Отчёт за месяц

#### 3.24 Отчёта нет на стенде

Фронт подключён по [reports-api.md](reports-api.md), но на
`setanta.pythonanywhere.com` эндпоинтов нет (27.09):

```
GET /contracts/16/reports          → 404
GET /contracts/16/reports/2026-01  → 404
```

В схеме по-прежнему 48 операций и ни одного пути `/reports`. Проверяли на
ответах из описания, подменяя их в браузере. **Нужно:** выкатить на стенд —
тогда пройдём сценарии вживую.

#### 3.25 У эфиров нет хронометража и просмотров

Лист `live_event` — дата, время, турнир, событие. В прежней таблице эфиров
(«Live spot») были ещё канал, `Pre`, `Mid 1`, `Mid 2`, `Post`, просмотры и
строки «Итого»: число спотов и вставок, секунды по колонкам, просмотры. Фронт
показывает лист как в API, эти колонки и итоги ушли.

**Нужно решить:** есть ли эти данные в исходном файле. Если есть — добавить
их в `LiveEventRow`, и итоги вернутся. Если нет — вопрос снят.

#### 3.26 У ошибок разбора файла нет кода

`details` — только текст. Фронт показывает для файла за чужой месяц отдельное
предупреждение и узнаёт этот случай по началу строки «Файл не за выбранный
месяц». Поменяется формулировка на сервере — предупреждение молча
превратится в общий список.

**Нужно:** `code` в каждой записи `details`, например `wrong_period`,
`missing_sheet`, `bad_date`.

### Кампании

#### 3.27 Заявку можно завести без ролика

Площадка принимала в работу кампании, которые нечем показывать. Фронт теперь
не даёт отправить заявку без ролика, но сервер `POST /campaigns` без
`creativeId` и `creativeUrl` по-прежнему принимает — обойти форму нетрудно.

**Нужно:** на создании требовать `creativeId` или `creativeUrl`, иначе `400`
с полем `creativeId` в `fields`.

### Закрыто

- **Файлы** — загрузка, `fileId`, `creativeId`, `logoId`, отдача по слагу без
  токена. Фронт на этом уже работает: логотип и ролик грузятся файлом,
  скачивание идёт обычной ссылкой.
- **Учётки на стенде** — есть `viewer`, `cola` (Coca Cola) и `artel` (Artel).
  Роли `advertiser` проверена вживую; `viewer` — ещё нет, см. 5.
- **Демо-данные** — 40 кампаний по двум брендам, залиты нашими сидерами
  (`scripts/seed-mock-campaigns.mjs`).
- **Осиротевшие файлы на стенде** — при проверке 3.3 и 3.4 мы залили два
  пробных файла (`probe-logo.png`, `probe-creative.mp4`). К сущностям они не
  привязаны; удалить их нечем, см. 3.23.

## 4. Чего нет вообще: разделы на моке

Данные лежат в `src/lib/*Seed.js` и правятся в localStorage; форматы описаны
по факту того, что рисует интерфейс. Ниже — конспект; разбор по разделам,
с форматами строк и эндпоинтами, вынесен в [backend-mock.md](backend-mock.md).

### 4.1 Обзор — помесячный отчёт площадки

Экран `/app/overview`. Один документ на месяц, админ правит его прямо на
странице, viewer только смотрит.

```
GET   /overview?period=2026-08     → OverviewReport
PUT   /overview/2026-08            → OverviewReport   (admin)
```

| Блок                    | Поля                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------- |
| `summary`               | заголовок, подзаголовок, число публикаций, охват в соцсетях                            |
| `mediaTotals[]`         | прямые эфиры, рекламные ролики, промо в эфире, хронометраж (сек.), просмотры Live Ads  |
| `socialChannels[]`      | канал (Instagram / Telegram), число публикаций, суммарный охват, охваты по публикациям |
| `audience`              | доля мужчин, заголовок и примечание к возрастной структуре                             |
| `ageShare[]`            | доли возрастных групп 13–17 / 18–24 / 25–34 / 35–44 / 45–54                            |
| `deviceShare[]`         | доли устройств: браузер, Smart TV, телефон, планшет                                    |
| `platformDeviceShare[]` | то же в разрезе OTT и TV                                                               |
| `leagueAgeRows[]`       | вид спорта, перечень лиг, распределение по четырём возрастным группам                  |

Цвета и иконки — забота фронта, в API не нужны. Источник: `src/lib/overviewSeed.js`.

### 4.2 Отчёты по кампании и договору

Экраны: статистика кампании (`/app/campaigns/:id`) и «Отчёт» у рекламодателя.
Отчёт привязан к **договору и месяцу**.

```
GET /reports/spot?contract=Д-2026/901&period=2026-08
```

- **Total statistic** — сводка по двум телеканалам: ролики, хронометраж, просмотры Live Ads, промо, OTT pre-roll.
- **Spot statistic** — то же в разрезе Setanta Sports 1 и 2: standard spot и live spot (UFC / Football), в штуках и секундах.
- **Лог выходов** — построчно: ролик, дата, время (GMT+4), канал. Выгрузка из «Шаблона импортируемого отчёта Setanta Statistics».
- **Промо** — тот же лог по промо-выходам.
- **Соцсети** — публикации Instagram и Telegram с охватами.
- **OTT** — live spot и pre-roll: показы и просмотры.
- **Медиаплан** — план размещения, редактируемая таблица.

Формат строк: `{ item, date, time, channel }` для логов, `{ label, value }` для
сводок. Если данные приходят выгрузкой из внешней системы — удобнее эндпоинт
загрузки файла отчёта плюс чтение по договору и месяцу. Формат лучше
обсудить до реализации: это самый большой кусок.

### 4.3 Динамика по дням для графика кампании

График за 14 дней (расход, показы, клики) сейчас генерируется на клиенте из
итоговых чисел — то есть выдуман.

```
GET /campaigns/:id/timeseries?metric=impressions&from=…&to=…  → [{ date, value }]
```

Если такого разреза в системе нет — скажите, график уберём.

### 4.4 Пользовательские вкладки и таблицы отчёта

Состав вкладок отчёта, загруженные таблицы спот-логов и правки сводок живут
в localStorage браузера — у каждого человека свои. Если это общие данные,
нужен серверный аналог: состав вкладок и содержимое таблиц по договору.

## 6. Порядок, который предлагаем

1. CORS (3.1) — добавить наши origin'ы. Пока всё держится на прокси.
2. Мелочи из раздела 3: `readOnly` у `advertiserId` (3.12), `409` в схеме
   (3.14), порядок выдачи (3.18), имя и почта админа (3.19).
3. Файлы: `inline` для роликов (3.20) и `id` у `AttachedFile` (3.21) — оба
   нужны, чтобы ролик договора переносился в кампанию так же, как свой.
4. Уникальность номера договора (3.9) — подтвердить или навесить.
5. Обзор — самый заметный раздел на моке.
6. Отчёты и логи выходов — самый большой кусок, формат обсудить заранее.

Разбор разделов на моке с полями и эндпоинтами — в
[backend-mock.md](backend-mock.md).
