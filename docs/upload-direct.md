# Загрузка роликов напрямую в хранилище

Задача бэкенду — пункт 3.28 в [backend.md](backend.md). Здесь — зачем, как
устроено и что именно нужно от API.

---

## 1. Что сейчас не так

Ролик уходит одним запросом `POST /api/v1/files` (multipart, `kind=creative`)
целиком. Путь файла:

```
браузер → прокси Vercel → setanta.pythonanywhere.com → диск PythonAnywhere
```

На ролике в 60 МБ это минуты ожидания:

- файл идёт через лишний узел (Vercel) и дальше на PythonAnywhere — далеко от
  пользователей в Узбекистане;
- PythonAnywhere держит веб-воркер всё время загрузки и упирается в свой
  лимит на длительность запроса;
- обрыв связи — загрузка с нуля, продолжить нельзя;
- части не грузятся параллельно — канал используется не полностью.

Фронт сам файл никак не обрабатывает: `FormData` уходит как есть. Ускорить
загрузку без бэка нельзя.

---

## 2. Как должно быть

Браузер грузит файл **прямо в объектное хранилище** частями, параллельно, по
подписанным ссылкам. Бэк выдаёт ссылки и регистрирует готовый файл, но сам
байты ролика не принимает.

```
1. браузер → бэк         POST /files/uploads               «хочу загрузить ролик»
   бэк     → браузер     uploadId + подписанные ссылки на части
2. браузер → хранилище   PUT каждой части (3–4 параллельно)
3. браузер → бэк         POST /files/uploads/:id/complete   номера частей и ETag
   бэк     → браузер     StoredFile — тот же, что сейчас отдаёт POST /files
```

Дальше всё как сегодня: `id` файла уходит в `creativeId`, ссылка
`/files/<slug>/download` работает.

### Хранилище

Любое S3-совместимое. Предлагаем **Cloudflare R2**: тот же API, что у S3
(`boto3` работает без изменений), и нет платы за скачивание — ролики
смотрят часто. Подойдёт и AWS S3, и Backblaze B2.

- Бакет **приватный**: читать и писать — только по подписанным ссылкам.
- **CORS бакета** — без него браузер не сможет сделать `PUT`:

  ```json
  [
    {
      "AllowedOrigins": [
        "https://setanta-prod.vercel.app",
        "https://setantadev.vercel.app",
        "http://localhost:5178"
      ],
      "AllowedMethods": ["PUT", "GET"],
      "AllowedHeaders": ["*"],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 3600
    }
  ]
  ```

  `ExposeHeaders: ETag` обязателен: без него фронт не прочитает ETag части и
  не сможет завершить загрузку.

- **Правило жизненного цикла**: прерывать незавершённые multipart-загрузки
  старше 1 дня — иначе брошенные части копятся и стоят денег.
- **PythonAnywhere**: на бесплатном тарифе исходящие запросы — только по
  белому списку. Проверьте, что с сервера доступен endpoint хранилища (на
  платном тарифе ограничения нет).

## 3. Эндпоинты

Все — с `Authorization`, как остальные. Роли — те же, что могут
`POST /files` сегодня.

### 3.1 `POST /files/uploads` — начать загрузку

Запрос:

```json
{
  "kind": "creative",
  "name": "artel-promo-30s.mp4",
  "size": 62914560,
  "mime": "video/mp4"
}
```

Бэк проверяет `kind`, тип и размер **по тем же правилам, что `POST /files`**,
заводит multipart-загрузку в хранилище (`CreateMultipartUpload`) и отвечает
`201`:

```json
{
  "uploadId": "u_7f3c9a",
  "partSize": 8388608,
  "parts": [
    {
      "number": 1,
      "url": "https://…r2.cloudflarestorage.com/…?partNumber=1&uploadId=…&X-Amz-Signature=…"
    },
    { "number": 2, "url": "https://…" }
  ],
  "expiresAt": "2026-10-24T14:00:00Z"
}
```

- `partSize` — 8 МБ (минимум S3 — 5 МБ на часть, кроме последней). Число
  частей = `ceil(size / partSize)`, файл меньше `partSize` — одна часть.
- Ссылки — `generate_presigned_url('upload_part', …)` на каждую часть, срок —
  1 час.
- Ключ объекта — случайный (`uuid`), **не** имя файла; имя храним в записи.
- `uploadId` — наш, не S3-шный: по нему бэк находит S3 `UploadId`, ключ и
  владельца. Чужой `uploadId` — `404`.

Ошибки — как у `POST /files`, `400` с полем в `fields`:

| Код                     | Когда                                                    |
| ----------------------- | -------------------------------------------------------- |
| `file_too_large`        | `size` больше лимита для `kind` — в `message` лимит в МБ |
| `file_type_not_allowed` | `mime` не подходит для `kind`                            |

### 3.2 `POST /files/uploads/:uploadId/complete` — завершить

Запрос — номера частей и ETag, которые хранилище вернуло на каждый `PUT`:

```json
{
  "parts": [
    { "number": 1, "etag": "\"a54357aff0632cce46d942af68356b38\"" },
    { "number": 2, "etag": "\"0c78aef83f66abc1fa1e8477f296d394\"" }
  ]
}
```

Бэк:

1. `CompleteMultipartUpload` с этим списком;
2. `HeadObject` — сверяет итоговый размер с заявленным `size` и лимитом
   (подписанный `PUT` размер части не ограничивает — проверяем здесь);
   не сошлось — удаляет объект и отвечает `400 file_too_large`;
3. заводит запись файла и отвечает `201` **тем же `StoredFile`**, что
   `POST /files`: `{id, name, url, size, mime, addedAt}`.

Ошибки: `404` — загрузки нет или истекла; `409 upload_parts_mismatch` — не
хватает частей или ETag не совпал.

### 3.3 `DELETE /files/uploads/:uploadId` — отменить

`AbortMultipartUpload`, запись загрузки удаляется. Ответ `204`. Фронт зовёт
его, когда пользователь жмёт «Отмена» или закрывает форму посреди загрузки.

### 3.4 Желательно: `GET /files/uploads/:uploadId` — продолжить после обрыва

Отдаёт уже загруженные части (`ListParts`) и свежие ссылки на недостающие —
в той же форме, что ответ 3.1. С ним после обрыва связи или перезагрузки
страницы фронт догружает только то, чего нет. Без него загрузка начнётся
заново — но по частям всё равно быстрее, чем сейчас.

## 4. Скачивание

`GET /files/<slug>/download` остаётся как есть — все сохранённые ссылки
продолжают работать. Для файлов в хранилище он отвечает `302` на подписанную
ссылку `GET` (срок — 10–15 минут) с параметром
`ResponseContentDisposition`:

- `video/*`, `image/*` — `inline`: ролик открывается во вкладке (это заодно
  закрывает 3.20);
- остальное — `attachment; filename="…"`, как сейчас.

Старые файлы на диске PythonAnywhere отдаются по-старому, переносить их не
обязательно.

---

## 5. Совместимость

- `POST /files` **оставляем**: логотипы и сканы договоров маленькие, им
  хватает и его. Новую схему фронт включит для `kind=creative` (и для любого
  файла больше 10 МБ).
- `StoredFile`, `creativeId`, `AttachedFile` — без изменений.
- Лимиты размера и типов — те же, что у `POST /files` сегодня. Хорошо бы
  отдавать их в `message` ошибки 3.1 — фронт покажет требования до загрузки.

## 6. Как проверить без фронта

```bash
# 1. начать
curl -X POST "$API/files/uploads" -H "Authorization: Bearer $T" \
  -H "Content-Type: application/json" \
  -d '{"kind":"creative","name":"probe.mp4","size":10485760,"mime":"video/mp4"}'

# 2. залить части (ссылки — из ответа; ETag — из заголовка ответа)
split -b 8388608 probe.mp4 part_
curl -i -X PUT --upload-file part_aa "$PART1_URL" | grep -i etag
curl -i -X PUT --upload-file part_ab "$PART2_URL" | grep -i etag

# 3. завершить
curl -X POST "$API/files/uploads/$UPLOAD_ID/complete" -H "Authorization: Bearer $T" \
  -H "Content-Type: application/json" \
  -d '{"parts":[{"number":1,"etag":"\"…\""},{"number":2,"etag":"\"…\""}]}'

# 4. скачивание — 302 на хранилище
curl -I "$API/files/<slug>/download"
```

И из браузера: `PUT` на ссылку части с `Origin: https://setanta-prod.vercel.app`
должен пройти CORS и отдать заголовок `ETag`.

---

## 7. Что сделает фронт

Когда эндпоинты появятся на стенде:

- ролик режется на части по `partSize` и грузится по 3–4 параллельно;
- часть, упавшая по сети, повторяется до трёх раз;
- прогресс в процентах, скорость и оставшееся время; «Отмена» —
  `DELETE /files/uploads/:id`;
- после `complete` всё как сейчас: `id` уходит в `creativeId`.

Остальные экраны правок не требуют — `StoredFile` тот же.
